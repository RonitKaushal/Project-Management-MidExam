How to write a 5-mark answer

Read this once before you start. It takes 1 minute.

A 5-mark Compiler Design answer needs around 1.5 to 2 pages in the exam. Examiners give marks for definition + diagram + example. Every answer in this book follows the same pattern, so you can copy the style straight into your answer sheet:

Symbols used in this book

SymbolMeaning
Boxed definitionWrite this word-for-word as your first line.
✎ Exam tipA small trick to get extra marks.
★ RememberA one-line memory hook.
HighlightedKeywords the examiner looks for.
Boxed resultFinal result of a derivation / proof. Box it in the exam!

For derivation and parsing questions, always write…

  1. The grammar (productions) and the input string.
  2. Every step on a new line with the ⇒ sign. Never skip a step.
  3. The parse tree for the derivation.
  4. For parsers: a Stack | Input | Action table.
  5. One line of conclusion (accepted / ambiguous / not ambiguous).
Grammar + string + steps + tree + box = full marks in derivation questions.

Q1Explain the phases of a compiler with a block diagram

5 marksUnit 1 · Introduction
A compiler is a program that reads a program written in one language (source program) and translates it into an equivalent program in another language (target program). The compiler does this job in a series of steps called phases.

Ans. There are mainly two parts of the compilation process:

  1. Analysis phase: breaks the source code into parts and arranges these pieces into a meaningful structure. It has three sub-parts: lexical analysis, syntax analysis and semantic analysis.
  2. Synthesis phase: builds the target program from that structure. It has three sub-parts: intermediate code generation, code optimization and code generation.

Block diagram

We follow the statement a := a + b * c * 2 through every phase, exactly as the notes do.

1Lexical analysis

  • Also called linear analysis or scanning.
  • The lexical analyzer reads the source program and breaks it into a stream of units called tokens.
  • It classifies the units into lexical classes (identifiers, constants, keywords etc.) and enters them into different tables.

2Syntax analysis

  • Also called hierarchical analysis or parsing.
  • The syntax analyzer checks each line of the code and spots every tiny mistake the programmer made while typing the code.
  • If the code is error-free, the syntax analyzer generates the tree.

3Semantic analysis

  • The semantic analyzer determines the meaning of a source string.
  • For example, matching of parentheses, matching of if…else, performing arithmetic operations that are type compatible, or checking the scope of operation.
  • In our example, the integer 2 is converted with int to float because the others are real.

4Intermediate code generation

The intermediate representation should have two properties: it should be easy to produce and easy to translate into the target program. We use three-address code, a sequence of instructions each having at most three operands:

t1 = inttoreal(2)
t2 = id3 * t1
t3 = t2 * id2
t4 = t3 + id1
id1 = t4

5Code optimization

This phase attempts to improve the intermediate code so that we get faster-running code or less memory consumption. The overall running time of the target program improves:

t1 = id3 * 2.0
t2 = id2 * t1
id1 = id1 + t2

6Code generation

The target code is generated. The intermediate instructions are translated into a sequence of machine instructions:

MOV id3, R1
MUL #2.0, R1
MOV id2, R2
MUL R2, R1
MOV id1, R2
ADD R2, R1
MOV R1, id1

Two helpers used by all phases

  • Symbol table: a data structure that stores names found in the source program (variables, procedures, keywords, constants, class names, label names) with their attributes.
  • Error detection & recovery: each phase can find errors (lexical, syntax, semantic) and must deal with them so that compilation can continue.

Q2Structure of a compiler, symbol table and error handler

5 marksUnit 1 · Introduction
A compiler translates a source program into an equivalent target program. Structurally it is made of an analysis part (front end) and a synthesis part (back end), both supported by a symbol table and an error handler.

Ans. Major functions done by a compiler (from the notes):

  • Convert one form of program to another.
  • Generate target machine code that is easy to understand.
  • Preserve the meaning of the source code.
  • Report errors that occur during the compilation process.
  • Do the compilation efficiently.

Structure: front end and back end

Front endBack end
Phases that depend mainly on the source language, largely independent of the target machine.Phases that depend on the target machine and do not depend on the source program.
Lexical, syntax and semantic analysis, intermediate code generation and creation of the symbol table. Some code optimization too.Code optimization and code generation, with the necessary error handling and symbol table operations.

Pass: one complete scan of the source program (read an input file, write an output file). Several phases may be grouped into one pass.

Role of the symbol table

A symbol table is a data structure used by a language translator such as a compiler or interpreter. It stores the names found in the source program along with the relevant attributes of those names. It is used by both the analysis and synthesis phases.

What it stores

  • Variables / identifiers
  • Procedures / functions
  • Keywords
  • Constants
  • Class names
  • Label names

What it is used for

  • Store all names in one structured place
  • Verify whether a variable has been declared
  • Determine the scope of a name
  • Type checking of assignments and expressions

Each entry has the format <symbol name, type, attribute>. For static int salary the entry is <salary, int, static>.

  • insert(): used mostly in the analysis phase when tokens are identified, e.g. int x; is processed as insert(x, int).
  • lookup(): searches a name to check if it exists, was declared before use, is in scope, is initialised, or is declared more than once.
  • Implementation: linear (sorted / unsorted) list, binary search tree or hash table (most common).

Role of the error handler

The error detection and recovery box in Fig 1.1 is connected to every phase. A compiler should report errors and then recover so it can continue and find more errors.

Error typeFound in phaseTypical examples
LexicalLexical analysisSpelling errors, too-long identifiers or constants, illegal characters, e.g. x = 1xab;
SyntaxSyntax analysisErrors in structure, missing operators, unbalanced parentheses, e.g. x = (3 + 5;
SemanticSemantic analysisIncompatible operand types, undeclared variable, actual and formal arguments not matching, e.g. int a = "hello";

Error recovery strategies:

  1. Panic mode: discard input symbols one at a time until a synchronizing token (like ; or end) is found. Simple and never goes into an infinite loop.
  2. Phrase level: do a local correction on the remaining input, e.g. replace a comma by a semicolon or insert a missing semicolon.
  3. Error production: add productions for common errors to the grammar so a proper message can be generated.
  4. Global correction: find a parse tree for a related correct string using the minimum number of insertions, deletions and changes. Mostly theoretical.

A compiler is structured as a front end (analysis) and a back end (synthesis). The symbol table keeps information about every name for all phases, and the error handler detects, reports and recovers from lexical, syntax and semantic errors.

Q3What is lexical analysis? Explain tokens, lexemes and patterns

5 marksUnit 2 · Lexical Analysis
Lexical analysis (also called linear analysis or scanning) is the first phase of a compiler. It reads the input characters of the source program and produces as output a sequence of tokens that the parser uses for syntax analysis.

Ans. The lexical analyzer reads the source program and breaks it into a stream of units called tokens. It then classifies these units into different lexical classes, e.g. identifiers, constants and keywords, and enters them into different tables (like the symbol table).

1Token

A token is a sequence of characters having a collective meaning.

Typical tokens are: 1) identifiers 2) keywords 3) operators 4) special symbols 5) constants.

2Pattern

A pattern is the set of rules associated with a token. It describes which strings belong to that token, e.g. "letter followed by letters and digits" for an identifier.

3Lexeme

A lexeme is the sequence of characters in the source program that is matched with a pattern for a token.

Example 1: total = sum + 12.5

Example 2: a := a + b * c * 2

Tokens: id1 := id1 + id2 * id3 * 2. Here a, b and c are identifiers (entered in the symbol table as id1, id2, id3), := is the assignment sign, + and * are operators and 2 is a number.

Lexical analysis is the first phase of the compiler. It groups characters into lexemes, matches each lexeme against a pattern and passes the resulting tokens to the parser.

Q4Functions and responsibilities of the lexical analyzer

5 marksUnit 2 · Lexical Analysis
The lexical analyzer is the first phase of the compiler. Its main task is to read the input characters and produce as output a sequence of tokens that the parser uses for syntax analysis.

Ans. The lexical analyzer works together with the parser. It is implemented as a subroutine of the parser.

Functions / responsibilities

  1. Read the source program: it scans the input string from left to right, one character at a time.
  2. Produce tokens: on receiving a "get next token" command from the parser, it reads input characters until it can identify the next token, and returns it.
  3. Classify lexemes: it puts each unit into a lexical class (identifier, keyword, operator, constant, special symbol) by matching it with a pattern.
  4. Enter names in the symbol table: identifiers and constants are entered in tables so that later phases can use them.
  5. Strip comments and white space: as a secondary task at the user interface, it removes comments and white space (blanks, tabs and newline characters).
  6. Detect lexical errors: spelling errors, exceeding the length of identifiers or numeric constants, and appearance of illegal characters. Example: in x = 1xab;, 1xab is neither a number nor an identifier.
  7. Input buffering: it uses special buffering to reduce the overhead of processing each character (explained below).

Scanning + lexical analysis

Some lexical analyzers are divided into a cascade of two phases: the first is called scanning (does simple tasks) and the second is lexical analysis (does the more complex tasks).

Input buffering: buffer pair

  • A buffer is divided into two N-character halves (N = number of characters on one disk block). N characters are read into each half.
  • Two pointers are kept: lexeme_beginning marks the beginning of the current lexeme, and forward scans ahead until a pattern match is found. The string between them is the current lexeme.
  • Once the lexeme is found, forward is set to its right end, and after the token is returned lexeme_beginning moves to the character just after it.

Sentinels: a special character eof is placed at the end of each buffer half, so the scanner needs only one test per character to know when a half has ended.

Why keep it separate from the parser?

  • Simpler design, the most important reason.
  • Compiler efficiency is improved.
  • Compiler portability is enhanced.
The lexical analyzer reads characters, removes comments and white space, groups lexemes into tokens, enters names into the symbol table, reports lexical errors and hands tokens to the parser on every "get next token" request.

Q5Difference between lexical analysis and syntax analysis

5 marksUnit 2 · Lexical / Unit 3 · Parsing
Lexical analysis (scanning) reads characters and produces a stream of tokens.
Syntax analysis (parsing) takes those tokens and checks them against the grammar, producing a parse tree or an error message.

Ans. Both belong to the analysis phase of the compiler. The lexical analyzer is the first phase and the parser is the second. The parser obtains a string of tokens from the lexical analyzer.

Example 1: the same statement in both phases

Statement: total = sum + 12.5

  • Lexical analysis gives the tokens: total (id), = (relation), sum (id), + (operator), 12.5 (num).
  • Syntax analysis checks that "id = id + num" follows the grammar and builds the tree with = at the root, total on the left and + (sum, 12.5) on the right.

Example 2: different errors

Lexical error
x = 1xab;
1xab is neither a number nor an identifier, so a valid token cannot be formed.
Syntax error
x = (3 + 5;
Every token is valid, but the closing ")" is missing, so the grammar rule fails.

Note: in fi ( ) { }, "fi" is not reported as a misspelling of if. The lexical analyzer treats it as a valid identifier, so lexical analysis alone cannot find every mistake.

Why are they separated?

  • Simpler design
  • Better compiler efficiency
  • Better compiler portability
Lexical analysis works on characters and produces tokens using patterns. Syntax analysis works on tokens and produces a parse tree using a context-free grammar. Together they form the first two steps of the analysis phase.

Q6Define CFG and explain its components with an example

5 marksUnit 3 · Grammar
A Context-Free Grammar (CFG) is a 4-tuple G = (V, T, P, S) that describes the syntax (structure) of a language. Every production has a single variable on the left-hand side.

Ans. The parser checks the tokens against the rules of a formal grammar. In compilers that grammar is a context-free grammar. It is used for parsing, derivations and parse trees.

Components of a CFG

4-tupleG = ( V , T , P , S )

TTerminalsA finite set of terminals: the actual symbols / tokens, e.g. id, +, *, (, ).
PProductionsA finite set of rules of the form A → α, where A is a variable and α ∈ (V ∪ T)*.

Using the grammar: deriving 3*2+5

A string belongs to the language if it can be derived from the start symbol by replacing variables using productions:

E ⇒ E * E
  ⇒ I * E
  ⇒ 3 * E
  ⇒ 3 * E + E

Another example (notes, Unit 3)

Always write "G = (V, T, P, S)" and explain each letter in one line. Then identify V, T, P, S for your own example grammar.
A CFG G = (V, T, P, S) consists of variables, terminals, productions and a start symbol. It defines the syntax of a programming language and is the base for derivations, parse trees and parsing.

Q7Explain leftmost and rightmost derivations with examples

5 marksUnit 3 · Derivation
A derivation is a sequence of steps in which we start from the start symbol and, at every step, replace one non-terminal by the body of one of its productions, until only terminals (the input string) remain.

Ans. There are mainly two types of derivations:

  1. Leftmost derivation (LMD): a derivation of a string W in grammar G is a leftmost derivation if at every step the leftmost non-terminal is replaced.
  2. Rightmost derivation (RMD): a derivation of a string W in grammar G is a rightmost derivation if at every step the rightmost non-terminal is replaced.

Grammar used (from the notes)

Q8What is a parse tree? How is it constructed from a CFG?

5 marksUnit 3 · Parse tree
A parse tree (derivation tree) is a tree that shows how a string is derived from the start symbol of a grammar. Its root is the start symbol, its interior nodes are non-terminals and its leaves are terminals.

Ans. The parser obtains a string of tokens from the lexical analyzer, and its output is some representation of the parse tree for that stream of tokens. If the string is a valid sentence of the grammar, the parser produces a parse tree; otherwise it gives an error message.

Properties of a parse tree

  • The root is labelled by the start symbol.
  • Every interior node is a non-terminal; its children are the symbols of the body of the production used.
  • Every leaf is a terminal (or ε).
  • Reading the leaves from left to right gives the input string (the "yield").
  • It represents the concrete syntax of a program.

Steps to construct a parse tree from a CFG

  1. Write the start symbol as the root.
  2. Pick the production used in the next derivation step (e.g. leftmost derivation).
  3. Make the symbols of that production's body the children of the non-terminal, from left to right.
  4. Repeat for every non-terminal leaf until all leaves are terminals.
  5. Check: the leaves read left to right must equal the input string.

Example: id + id * id

Grammar (from the notes): E → E+E | E*E | id

E ⇒ E + E
  ⇒ id + E
  ⇒ id + E * E
  ⇒ id + id * E
  ⇒ id + id * id

Parse tree vs syntax tree (Table 3.1.1 of the notes)

No.Parse treeSyntax tree
1Interior nodes are non-terminals, leaves are terminals.Interior nodes are "operators", leaves are operands.
2Rarely constructed as a data structure.Usually used when representing a program in a tree structure.
3Represents the concrete syntax of a program.Represents the abstract syntax of a program (the semantics).
A parse tree shows how the start symbol of a CFG derives the input string. It is built by placing the start symbol at the root and expanding each non-terminal with the body of the production used, until every leaf is a terminal and the leaves spell the input.

Q9Explain ambiguity in grammar. How is it identified using parse trees?

5 marksUnit 3 · Ambiguity
An ambiguous grammar is one that produces more than one leftmost derivation or more than one rightmost derivation (that is, more than one parse tree) for the same sentence.

Ans. Formally (handbook): G = (V, T, P, S) is said to be ambiguous if and only if there exists a string in T* that has more than one parse tree. A grammar for which every string has exactly one parse tree is unambiguous.

How to identify ambiguity using parse trees

  1. Pick a string that uses the "doubtful" productions (usually an operator used twice, e.g. a+a+a).
  2. Try to derive it in two different ways (two LMDs or two RMDs).
  3. Draw the parse tree for each derivation.
  4. If the two trees have different shapes for the same string, the grammar is ambiguous.

Example 1 (notes): prove S → S+S | S−S | S*S | S/S | (S) | a is ambiguous

String: a+a+a

⇒ a+a+a

⇒ a+S+S
⇒ a+a+S

Here we have two leftmost derivations (two different parse trees) for the same string, hence the grammar is ambiguous.

Example 2 (notes): prove S → a | Sa | bSS | SSb | SbS is ambiguous

Two leftmost derivations exist, so this grammar is also ambiguous.

Example 3 (handbook): E → E+E | id with id+id+id

Two parse trees can be created from the same grammar rules for id+id+id; both trees are different, hence the grammar is ambiguous.

Why ambiguity is a problem

  • The parser cannot decide which tree (which meaning) is correct, e.g. 3*2+5 can be grouped as (3*2)+5 or 3*(2+5).
  • Ambiguous grammars are not allowed in any parser except the operator precedence parser.

Other ambiguous grammars (handbook): S → aS | Sa | ε; E → E+E | E*E | id; A → AA | (A) | a. Unambiguous: S → (L) | a, L → LS | S.

A grammar is ambiguous if one string has more than one leftmost derivation, rightmost derivation or parse tree. We identify it by deriving one string in two ways and showing that the two parse trees are different.

Q10Differentiate between top-down and bottom-up parsing

5 marksUnit 3 · Parsing
Parsing is a technique that takes an input string and produces either a parse tree (if the string is a valid sentence of the grammar) or an error message. Parsing methods are classified as top-down or bottom-up.

Ans. In top-down parsing the parser builds the parse tree from top to bottom (root to leaves). In bottom-up parsing the parser starts from the leaves and works up to the root. In both cases the input is scanned from left to right, one symbol at a time.

Q11Explain the concept and working of top-down parsing with an example

5 marksUnit 3 · Parsing
Top-down parsing parses the input and starts constructing a parse tree from the root node (start symbol), gradually moving down to the leaf nodes. It follows a leftmost derivation of the input string.

Ans. Top-down parsers start from the start symbol and match the input string against the production rules, replacing a non-terminal when a rule matches. The input is read from left to right.

Working (steps)

  1. Start with the start symbol as the root.
  2. Take the leftmost non-terminal and choose one of its productions.
  3. Compare the terminals produced with the next input symbols.
  4. If they match, advance the input pointer and continue with the next non-terminal.
  5. If they do not match, try another production (backtracking) or report an error.
  6. The string is accepted when all input is matched and the tree is complete.

Example (handbook): input "read"

S → rXd | rZd
X → oa | ea
Z → ai
  1. Start with S. The production S → rXd matches the leftmost input letter r, so the parser advances to e.
  2. It expands X and tries X → oa from the left. "o" does not match "e".
  3. So the parser backtracks and tries the next production X → ea. Now "e" and "a" match.
  4. Finally "d" matches. All input letters are matched in order, so the string is accepted.

Problems with top-down parsing

1. Backtracking

As seen above, if the wrong production is chosen the parser has to go back and try another one. This wastes time.

2. Left recursion

A grammar is left recursive if it has a non-terminal A such that A ⇒ Aα. If left recursion is present, the parser may go into an infinite loop, because S keeps producing another S without checking any condition. It is removed as:

S → Sa | Sb | c | d   becomes   S → cS′ | dS′,  S′ → aS′ | bS′ | ε
E → E+T | T   becomes   E → TE′,  E′ → +TE′ | ε

3. Left factoring

If A → αβ1 | αβ2 (same prefix), the parser cannot tell which production to choose on seeing α. Left factoring rewrites it as A → αA′, A′ → β1 | β2 to defer the decision. Example: S → iEtS | iEtSeS | a becomes S → iEtSS′ | a, S′ → eS | ε.

Types of top-down parsers

  • Backtracking parser: tries productions one by one.
  • Recursive descent parser: one procedure per non-terminal.
  • Predictive / LL(1) parser: non-backtracking, table driven.
Top-down parsing builds the parse tree from the root to the leaves using leftmost derivation. It is simple, but the grammar must be free of left recursion and left factored to avoid infinite loops and backtracking.

Q12Explain recursive-descent parsing. Advantages and limitations

5 marksUnit 3 · Top-down parsing
A top-down parser that executes a set of recursive procedures to process the input without backtracking is called a recursive-descent parser. There is a procedure for each non-terminal in the grammar.

Ans. Recursive descent constructs the parse tree from the top, and the input is read from left to right. It is called "recursive" because it uses a context-free grammar, which is recursive in nature, and the procedures call each other recursively.

Working

  • Write one procedure for every non-terminal (variable).
  • The RHS of each production becomes the definition (body) of the procedure.
  • When the procedure sees an expected input symbol, it advances the input pointer to the next position.
  • For a non-terminal in the RHS, the procedure for that non-terminal is called.
  • If an unexpected symbol is seen, the procedure reports an error.

Example 1 (notes)

E → T {+T}*
T → V {*V}*
V → id
Procedure proc_E(tree_root);
var a, b : pointer to a tree node;
begin
  proc_T(a);
  While (nextsymb = '+') do
    nextsymb = next source symbol;
    proc_T(b);
    a = Treebuild('+', a, b);
  tree_root = a; return;
end proc_E;
Procedure proc_T(tree_root);
var a, b : pointer to a tree node;
begin
  proc_V(a);
  While (nextsymb = '*') do
    nextsymb = next source symbol;
    proc_V(b);
    a = Treebuild('*', a, b);
  tree_root = a; return;
end proc_T;
Procedure proc_V(tree_root); var a : pointer to a tree node;
begin If (nextsymb = 'id') then nextsymb = next source symbol; tree_root = tree_build(id, , );
       else print "Error"; return;
end proc_V;

Example 2 (handbook, C style)

Grammar: E → i E′,  E′ → + i E′ | ε  (l = lookahead)

int main() {
  E();   // E is start symbol
  if (l == '$')
    printf("Parsing Successful");
}
E() {
  if (l == 'i') { match('i'); E'(); }
}
E'() {
  if (l == '+') {
    match('+'); match('i'); E'();
  } else return;  // ε
}
match(char t) {
  if (l == t) l = getchar();
  else printf("Error");
}

After the last E′() returns, the lookahead is $, so "Parsing Successful" is printed.

Advantages (notes)

  • It is exceptionally simple.
  • It can be constructed from recognizers simply by doing some extra work (building the tree with Treebuild).
  • One procedure per non-terminal, so it is easy to write by hand.

Limitations / disadvantages

  • It is time consuming (many recursive calls).
  • It is difficult to provide good error messages.
  • If the grammar is not left factored, it cannot avoid backtracking.
  • Left recursion must be removed first, otherwise a procedure calls itself forever (infinite loop). That is why the handbook rewrites E → E+T | T as E → TE′, E′ → +TE′ | ε before writing the procedures.

A form of recursive-descent parsing that does not require any backtracking is known as predictive parsing.

A recursive-descent parser is a top-down parser with one recursive procedure per non-terminal. It is very simple to build, but it is slow, gives poor error messages and needs a grammar without left recursion and with left factoring.

Q13Explain predictive parsing. Working and conditions for an LL(1) parser

5 marksUnit 3 · Top-down parsing
Predictive parsing is a form of top-down (recursive-descent) parsing that does not require any backtracking. The LL(1) parser is a non-recursive, table-driven predictive parser.

Ans. The name LL(1) means:

LL(1)
Input is scanned from left to rightUses leftmost derivation for the input stringUses only one input symbol (lookahead) to predict the parsing action

Model of the LL(1) parser

Data structures used: input buffer (input string followed by $), stack (grammar symbols, $ at the bottom) and the parsing table M.

Working

  1. Initially the stack holds $E (start symbol on top of $) and the input buffer holds the string followed by $.
  2. The parsing program reads the top of the stack (X) and the current input symbol (a). These two symbols decide the action.
  3. If X is a non-terminal, the parser consults the table entry M[X, a] and replaces X on the stack by the body of that production (rightmost symbol pushed first). Because the table is consulted every time, this is called table-driven parsing.
  4. If X is a terminal equal to a, X is popped and the input pointer moves to the next symbol (match).
  5. If M[X, a] is blank, the parser reports an error.
  6. The input is successfully parsed when the stack is empty ($) and the next token is $ (halting configuration).

Steps to construct an LL(1) parser

  1. Remove left recursion / perform left factoring.
  2. Compute FIRST and FOLLOW of the non-terminals.
  3. Construct the predictive parsing table.
  4. Parse the input string with the help of the parsing table.

Conditions for a grammar to be LL(1)

  1. No left recursion: A → Aα must be removed, otherwise the parser loops forever.
  2. Left factored: no two alternatives of a non-terminal may start with the same prefix, so one lookahead symbol is enough to choose.
  3. Not ambiguous: ambiguous grammars are not allowed in any parser except operator precedence.
  4. One entry per cell: every entry M[A, a] of the parsing table must have at most one production, so the action is predicted uniquely with one symbol of lookahead.

Example (notes)

E → E+T | T, T → T*F | F, F → (E) | id is left recursive, so it is not LL(1). After removing left recursion it becomes:

E → TE′    E′ → +TE′ | ε
T → FT′    T′ → *FT′ | ε
F → (E) | id

Its parsing table has only one production in every cell, so this grammar is LL(1) and parses id+id*id successfully (see Q14).

A predictive (LL(1)) parser is a non-backtracking, table-driven top-down parser that uses a stack, an input buffer and a parsing table, and decides each move from the top of the stack and one lookahead symbol. The grammar must be free of left recursion, left factored, unambiguous and give a table with at most one entry per cell.

Q15Explain bottom-up parsing. How is the parse tree built from input to start symbol?

5 marksUnit 3 · Bottom-up parsing
Bottom-up parsing starts from the leaf nodes of a tree and works in the upward direction till it reaches the root node. We start from the sentence and apply production rules in reverse to reach the start symbol.

Ans. While a top-down parser expands the start symbol, a bottom-up parser does the opposite: it repeatedly finds a substring of the input that matches the right side of a production (a handle) and reduces it to the non-terminal on the left side. This traces a rightmost derivation in reverse.

How the tree is built (steps)

  1. Start with the input string; each token is a leaf of the tree.
  2. Scan the input from left to right and find a handle: a substring that matches the RHS of a production.
  3. Reduce it: replace the handle by the LHS non-terminal. In the tree, this creates a new parent node above those symbols.
  4. Repeat until only the start symbol remains. That symbol is the root and the tree is complete.
  5. If no handle can be found and the start symbol is not reached, an error is reported.

Example: id + id * id

Grammar (notes): E → E+T | T,  T → T*F | F,  F → id

StepString (sentential form)Reduction used
0id + id * idinput
1F + id * idF → id
2T + id * idT → F
3E + id * idE → T
4E + F * idF → id
5E + T * idT → F
6E + T * FF → id
7E + TT → T*F
8EE → E+T  start symbol reached

Reading the reductions from bottom to top gives the rightmost derivation: E ⇒ E+T ⇒ E+T*F ⇒ E+T*id ⇒ E+F*id ⇒ E+id*id ⇒ T+id*id ⇒ F+id*id ⇒ id+id*id.

Types of bottom-up parsers

  • Shift-reduce parser: the general method, using a stack and input buffer.
  • Operator precedence parser: for operator grammars (no ε and no two adjacent non-terminals).
  • LR parsers: SLR, CLR, LALR (the most efficient bottom-up methods).
Bottom-up parsing builds the parse tree from the input symbols (leaves) up to the start symbol (root) by repeatedly reducing handles. The sequence of reductions is a rightmost derivation traced in reverse.

A shift-reduce parser constructs the parse tree in a bottom-up manner, from the leaves (bottom) to the root (up), using a stack and an input buffer. A more general form of shift-reduce parser is the LR parser.

  • An input buffer for storing the input string (ending with $).

Q17What is handle pruning? Explain its role in bottom-up parsing

5 marksUnit 3 · Bottom-up parsing
Handle: a handle of a string is a substring that matches the right side of a production, and whose reduction to the non-terminal of that production is one step along the reverse of a rightmost derivation.
Handle pruning: the process of discovering a handle and reducing it to the appropriate left-hand-side non-terminal is known as handle pruning.

Ans. A bottom-up parser must decide, at each step, which substring to reduce. Not every substring that matches a right side is correct; only the handle leads back to the start symbol. Repeated handle pruning gives the rightmost derivation in reverse.

Example (notes): id1 + id2 * id3

Grammar: E → E+E | E*E | id

Link with rightmost derivation

Reading the table from the bottom to the top gives a rightmost derivation:

E ⇒ E+E ⇒ E+E*E ⇒ E+E*id3 ⇒ E+id2*id3 ⇒ id1+id2*id3

So handle pruning = rightmost derivation in reverse.

Role in bottom-up parsing

  • Every bottom-up parser is a handle-pruning parser: at each step it finds the handle and reduces it.
  • In a shift-reduce parser, symbols are shifted until the handle appears on the top of the stack, then the reduce action prunes it (see Q16).
  • In an operator precedence parser, the handle is the string between <· and ·>, e.g. in $ <· id ·> + …, the handle id is reduced by F → id.
  • In LR parsers, the parsing table tells exactly when a handle is on the stack.
  • Choosing the correct handle decides whether the parse succeeds or wrongly gets stuck.
A handle is the right side of a production whose reduction is one step of the reverse rightmost derivation. Handle pruning, finding and reducing handles again and again, is the basic operation of every bottom-up parser and leads the input back to the start symbol.

Q19Explain the basic idea of LR parsing. How is it different from top-down parsing?

5 marksUnit 3 · LR parsing
LR parsing is the most efficient method of bottom-up parsing, which can be used to parse a large class of context-free grammars. The technique is called LR(k) parsing.

Ans. The name LR(k) means:

LRk
Left to right scanning of the inputConstructing a rightmost derivation in reverseNumber of input symbols of lookahead used to make parsing decisions

Types of LR parsers

  • LR(0)
  • SLR (Simple LR): small tables, simple generator
  • CLR (Canonical LR)
  • LALR (Lookahead LR)

Model of an LR parser

It has an input buffer for the input string, a stack for grammar symbols and states, an output, and a parsing table with two parts: action and goto.

  • ACTION[i, a] (state i, terminal a or $) has one of four values: shift j, reduce A → β, accept, error.
  • GOTO[i, A] gives the next state after a reduction to non-terminal A.

Basic idea of construction (LR(0))

  • Augmented grammar: add S′ → S, so the parser knows when to stop and accept. E.g. S → AA, A → aA | b becomes S′ → S, S → AA, A → aA | b.
  • LR(0) item: a production with a dot at some position, e.g. S → ABC gives S → .ABC, S → A.BC, S → AB.C, S → ABC.
  • Closure() and Goto() build the sets of items (states of a DFA), which are converted into the action/goto table.
  • If a state has both a shift and a reduce (SR conflict) or two reduces (RR conflict), the grammar is not LR(0).

Properties of LR parsers

  • Can be constructed to recognize most programming languages for which a CFG can be written.
  • The class of grammars parsed by LR is a superset of those parsed by predictive parsers.
  • Works using a non-backtracking shift-reduce technique.
  • Can detect a syntactic error as soon as possible.

LR(k) parsing scans the input left to right, builds a rightmost derivation in reverse using k lookahead symbols, and is driven by an action/goto table. Unlike top-down parsing, it is bottom-up, never backtracks, accepts left-recursive grammars and handles a larger class of grammars.

Q20Process from source program to parse tree / syntax tree

5 marksUnit 1–3 · Full picture
The source program is turned into tokens by the lexical analyzer. The parser takes these tokens, checks them against the grammar by finding a derivation, and outputs a parse tree (or syntax tree), which goes on to semantic analysis.

Ans. We trace the statement a := a + b * c * 2 through the front part of the compiler.

1Lexical analysis: characters → tokens

  • The lexical analyzer reads the characters left to right and groups them into lexemes.
  • Each lexeme is matched with a pattern and returned as a token: a → id1, := → assignment sign, + → plus sign, b → id2, * → multiplication sign, c → id3, 2 → number.
  • Identifiers a, b, c are entered into the symbol table. White space and comments are removed.
  • It works as a subroutine: each time the parser says "get next token", it returns the next token.

2Grammar: the rules of the language

The parser checks the tokens against a context-free grammar G = (V, T, P, S). In the notes' style:

S → id := E
E → E + E | E * E | id | num

3Derivation: is the token string a valid sentence?

The parser finds a derivation from S to the token string (leftmost here, as a top-down parser would):

S ⇒ id := E
  ⇒ id := E + E
  ⇒ id := id + E
  ⇒ id := id + E * E
  ⇒ id := id + id * E
  ⇒ id := id + id * E * E
  ⇒ id := id + id * id * E
  ⇒ id := id + id * id * num

4Parsing: building the parse tree

Each derivation step adds children under a non-terminal. A top-down parser builds it from the root; a bottom-up parser builds the same tree from the leaves by reducing handles.

5Syntax tree

Removing the non-terminals and keeping operators as interior nodes gives the syntax tree from the notes: := at the root with children a and +; + has children a and *; * has children b and another *, whose children are c and 2 (see Fig 1.2 in Q1). The semantic analyzer then adds int to float for 2.

Grammartokensrules to check against

The lexical analyzer converts characters into tokens and fills the symbol table; the parser, guided by the grammar, finds a derivation for the token string and builds the parse tree, which is simplified into a syntax tree for the next phases.

Explanation of each point

  1. Input: a compiler reads and analyses the whole source program through all its phases; an interpreter picks up one instruction, processes it, then moves to the next.
  2. Intermediate code: a compiler produces intermediate code (e.g. three-address code t1 = id3 * 2.0 …) and then target code; an interpreter does not create intermediate code.
  3. Memory: a compiler keeps the whole program, intermediate code, symbol table and target code, so it needs more memory; an interpreter holds only the current instruction.
  4. Errors: a compiler reports errors after checking the complete program; an interpreter stops and reports an error at the instruction where it occurs.
  5. Examples: C is compiled (C compiler); BASIC is interpreted.

What a compiler must do (major functions)

  • Convert the source program to target machine code that is easy to understand.
  • Preserve the meaning of the source code.
  • Report errors that occur during compilation.
  • Do the compilation efficiently.
Both are translators. A compiler translates the entire program, generates intermediate code, needs more memory and reports errors after the whole program (e.g. C). An interpreter takes one instruction at a time, has no intermediate code, needs less memory and reports errors per instruction (e.g. BASIC).
